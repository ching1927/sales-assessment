# 評分與成績單資料庫（assess_schema.sql）說明

> 狀態：**尚未執行**，兩個 SQL 檔都還沒在任何資料庫跑過，待老闆同意後才執行。

## 一、這是什麼

在既有的人員名冊（roster_schema.sql）與考題抽選器題庫旁邊，新增「考核評分」所需的資料表與函式。
前端只能呼叫函式，不能直接寫資料表；**分數一律由資料庫算**，不信任前端傳來的任何分數。
不會修改、刪除舊考題抽選器的任何東西，新增的名稱全部以 `assess_` 或 `assessment` 開頭。

## 二、三張資料表

| 資料表 | 放什麼 | 誰看得到 |
|---|---|---|
| `assessments` | 一場考核：考生、考生姓名（暱稱或姓名，開始當下的快照 `employee_label`）、門市（開始當下的快照）、考官、狀態（草稿／已送出／作廢）、新人或正式、總分、判定、合格線、最弱面向、作廢資訊 | 見下方權限表 |
| `assessment_items` | 一場裡的每個題組：分類、代號、七面向等級、題組分數、各面向得分、不適用面向、最弱面向（不含機密） | 與所屬考核相同 |
| `assessment_item_secrets` | 機密：題庫題號（question_id）、抽之前是否已在 drawn（was_drawn_before）、題組名稱、步驟與考點快照、考官備註（題號也算機密，所以主管與店長讀 `assessment_items` 看不到） | **只有客服部** |

另有檢視 `assessment_summaries`（成績單列表，不含機密欄位，以查詢者本人權限讀取，所以權限規則照樣生效）。

## 三、函式清單（只有客服部能用，其他人一律回「沒有權限」）

| 函式 | 做什麼 |
|---|---|
| `assess_candidates()` | 回傳納入考核且在職的員工 |
| `assess_categories()` | 各分類總題數與本輪剩餘 |
| `assess_start(員工編號, 手動身分)` | 開始考核。有到職日→自動算新人（含第 90 天）／正式，忽略手動身分；到職日空白→必須指定「新人」或「正式」，記「手動指定」。同考官同員工已有草稿→回傳既有那張 |
| `assess_draw(考核id, 分類陣列)` | 每個分類抽一個題組；優先避開該考生考過的（已送出與已作廢的算考過，草稿不算）；整個分類都考過才重複並回 `repeated=true` |
| `assess_save_item(題組id, 評分, 備註)` | 暫存評分，可只填部分面向；備註傳空白＝清除備註 |
| `assess_submit(考核id)` | 檢查七面向齊全，由資料庫算分，存成績單 |
| `assess_void(考核id, 原因)` | 作廢已送出的成績單（原因必填，不刪除） |
| `assess_abandon(考核id)` | 放棄草稿並刪除；本次才抽進 drawn 的題回到題池。**任一客服部都可以放棄任何人的草稿**（避免考官離職後草稿卡住題池）；抽題、暫存、送出仍限建立者本人 |
| `assess_score_item`、`assess_score_session`、`assess_verdict` | 純計算（不碰資料），給驗證與前端預覽用 |

### 計分規則（資料庫內建）

- 七面向配分：資訊正確性 20、預設訊息運用 15、問題掌握 15、主動引導 15、風險意識 15、語氣與禮貌 10、文字品質 10。
- 等級：優 100%、良 70%、待加強 40%、不及格 0%，另有「不適用」（每題組最多 2 個，七面向必須全有值）。
- 題組分數 ＝ Σ(適用面向配分 × 等級%) ÷ 適用配分合計，四捨五入到小數 1 位。
- 總分 ＝ 各題組「已四捨五入的題組分數」平均，再四捨五入到小數 1 位。
- 判定（依考核當天身分）：新人 ≥85 優秀、≥70 及格、≥60 需複訓、其餘不及格（合格線 70）；正式 ≥95 優秀、≥85 及格、≥75 需複訓、其餘不及格（合格線 85）。
  例：題組 77.5 分，新人「及格」、正式「需複訓」；70.0 分，新人「及格」、正式「不及格」；88.8 分，新人「優秀」、正式「及格」。
- 最弱面向：每題組取適用面向中等級最低者，並列全列；整場則每面向取各題組（該面向適用者）等級平均，最低者為最弱，並列全列。

| 客服部 cs_admin | 全部（含草稿、作廢） | 全部 | 可以 |
| 總公司主管 hq_viewer | 只看「已送出」 | 看不到 | 沒有權限 |
| 店長 store_manager | 只看自己門市且「已送出」 | 看不到 | 沒有權限 |
| 有登入但沒帳號 | 什麼都沒有 | 什麼都沒有 | 沒有權限 |
| 未登入 anon | 什麼都沒有 | 什麼都沒有 | 不能 execute |

所有人（包含客服部）都沒有直接 insert／update／delete 的權限，只能透過函式寫入。

## 五、怎麼執行（老闆同意之後）

1. 前提：`roster_schema.sql` 與考題抽選器的 `schema.sql` 都已執行過。
2. Supabase 專案 → SQL Editor → New query → 貼上 `assess_schema.sql` 整份 → Run。可重複執行，不會刪資料。
3. 再開新的 query → 貼上 `assess_verify_fake.sql` 整份 → Run。它只用假資料，**結尾一定 rollback，不留任何資料**。

## 六、驗證結果表怎麼看

執行完 `assess_verify_fake.sql` 後，最後一個結果是一張表，欄位為「序號／測項／預期／實際／通過」：

- 第 0 列「總結」會寫 `N/M 項通過`。**「通過」欄全部是「通過」才算驗證成功**。
- 有「失敗」的列：看「預期」與「實際」差在哪；測項名稱前半是分組（純計算、權限矩陣、流程、舊抽選器）。
- 某個區段若出現「意外中斷」，代表該區段有沒預期到的錯誤，「實際」欄就是錯誤訊息，請整張表貼給我。
- 因為 SQL Editor 只顯示最後一個結果，腳本把結果存在連線層級的預備陳述式（只含結果文字，不含資料）再 rollback、最後才顯示。為保險，rollback 前還會先顯示一次同樣的表，所以可能看到兩張一樣的表，看最後一張即可。
- 驗證會用掉幾個題庫流水號（rollback 也不會倒退），無害。

## 七、已知行為與已知限制

### 已知行為
- **調店後，舊成績單仍屬原門市**：成績單的門市歸屬用開始考核當下的門市快照（`store_code`），員工之後調店不會改。店長看得到的範圍以這個快照為準；調店員工的可見規則老闆之後再決定。
- **姓名也是快照**：成績單列表的姓名取自 `employee_label`（開始考核當下的暱稱或姓名），員工之後改暱稱、調店都不影響列表顯示，列表不依賴名冊。
- **同一位考官對同一員工重複開始考核**（含兩個請求同時進來）：不會報錯，回傳既有那張草稿。

### 抽題排序的取捨
挑題優先順序是：①該考生沒考過 ＞ ②本輪還沒被抽過 ＞ ③不是該分類上一次抽出的 ＞ ④隨機。
因為「該考生考過」優先於「本輪已被抽過」，重考者可能抽到本輪已被別人抽過的題。這符合老闆「優先避開考生考過的題組」的要求，是已知取捨。

### 已知限制
- 放棄考核時**不還原 `category_last`**（各分類最近一次抽出的題）。
- 若放棄期間該分類已開新一輪，放棄可能誤刪別場剛抽的 `drawn` 記錄（極少見）。
- 驗證腳本的結果表輸出若失敗，仍會 rollback，不會留下資料。
