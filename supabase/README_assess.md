# 評分與成績單資料庫（assess_schema.sql）說明

> 狀態：**尚未執行**，兩個 SQL 檔都還沒在任何資料庫跑過，待老闆同意後才執行。

## 一、這是什麼

在既有的人員名冊（roster_schema.sql）與考題抽選器題庫旁邊，新增「考核評分」所需的資料表與函式。
前端只能呼叫函式，不能直接寫資料表；**分數一律由資料庫算**，不信任前端傳來的任何分數。
不會修改、刪除舊考題抽選器的任何東西，新增的名稱全部以 `assess_` 或 `assessment` 開頭。

## 二、三張資料表

| 資料表 | 放什麼 | 誰看得到 |
|---|---|---|
| `assessments` | 一場考核：考生、考生姓名（暱稱或姓名，開始當下的快照 `employee_label`）、門市（開始當下的快照）、考官、狀態（草稿／已送出／作廢）、新人或正式、總分、判定、合格線、最弱面向、作廢資訊 | 見下方權限表 |
| `assessment_items` | 一場裡的每個題組：分類、代號、七面向等級、題組分數、各面向得分、不適用面向、最弱面向（不含機密） | 與所屬考核相同 |
| `assessment_item_secrets` | 機密：題庫題號（question_id）、抽之前是否已在 drawn（was_drawn_before）、題組名稱、步驟與考點快照、考官備註（題號也算機密，所以主管與店長讀 `assessment_items` 看不到） | **只有客服部** |
| `assessment_item_images` | 考官備註的圖片資料列：所屬題組、Storage 路徑、格式、大小 | 客服部全看；總公司主管只看已送出；店長只看自己門市且已送出（與所屬考核一致）。草稿、作廢的只有客服部 |

> 圖片資料表是第四張；備註「文字」、題組名稱、步驟仍只在 `assessment_item_secrets`，**只有客服部**。

另有檢視 `assessment_summaries`（成績單列表，不含機密欄位，以查詢者本人權限讀取，所以權限規則照樣生效）。

## 三、函式清單（只有客服部能用，其他人一律回「沒有權限」）

| 函式 | 做什麼 |
|---|---|
| `assess_candidates()` | 回傳納入考核且在職的員工 |
| `assess_categories()` | 各分類總題數與本輪剩餘 |
| `assess_start(員工編號, 手動身分)` | 開始考核。有到職日→自動算新人（含第 90 天）／正式，忽略手動身分；到職日空白→必須指定「新人」或「正式」，記「手動指定」。同考官同員工已有草稿→回傳既有那張 |
| `assess_draw(考核id, 分類陣列)` | 每個分類抽一個題組；優先避開該考生考過的（已送出與已作廢的算考過，草稿不算）；整個分類都考過才重複並回 `repeated=true` |
| `assess_save_item(題組id, 評分, 備註)` | 暫存評分，可只填部分面向；備註傳空白＝清除備註 |
| `assess_submit(考核id)` | 檢查七面向齊全，由資料庫算分，存成績單 |
| `assess_void(考核id, 原因)` | 作廢已送出的成績單（原因必填，不刪除） |
| `assess_abandon(考核id)` | 放棄草稿並刪除；本次才抽進 drawn 的題回到題池。**任一客服部都可以放棄任何人的草稿**（避免考官離職後草稿卡住題池）；抽題、暫存、送出仍限建立者本人。**回傳該草稿所有圖片的路徑清單（text[]）**，前端要依清單去 Storage 刪檔（資料庫不直接刪 Storage 檔案） |
| `assess_add_image(題組id, 路徑, mime, 大小)` | 新增備註圖片資料列（檔案先由前端傳到 Storage）。只限草稿且本人；格式限 jpeg／png／webp；大小 ≤ 2MB；路徑必須以「考核id/題組id/」開頭；每題組最多 5 張。回傳圖片 id |
| `assess_remove_image(圖片id)` | 移除圖片資料列並回傳 `storage_path`，前端據此刪 Storage 檔案。只限草稿且本人 |
| `assess_safe_uuid(文字)` | 內部輔助：安全轉 uuid，格式不對回傳 null 不報錯（Storage 權限規則用） |
| `assess_score_item`、`assess_score_session`、`assess_verdict` | 純計算（不碰資料），給驗證與前端預覽用 |

### 計分規則（資料庫內建）

- 七面向配分：資訊正確性 20、預設訊息運用 15、問題掌握 15、主動引導 15、風險意識 15、語氣與禮貌 10、文字品質 10。
- 等級：優 100%、良 70%、待加強 40%、不及格 0%，另有「不適用」（每題組最多 2 個，七面向必須全有值）。
- 題組分數 ＝ Σ(適用面向配分 × 等級%) ÷ 適用配分合計，四捨五入到小數 1 位。
- 總分 ＝ 各題組「已四捨五入的題組分數」平均，再四捨五入到小數 1 位。
- 判定（依考核當天身分）：新人 ≥85 優秀、≥70 及格、≥60 需複訓、其餘不及格（合格線 70）；正式 ≥95 優秀、≥85 及格、≥75 需複訓、其餘不及格（合格線 85）。
  例：題組 77.5 分，新人「及格」、正式「需複訓」；70.0 分，新人「及格」、正式「不及格」；88.8 分，新人「優秀」、正式「及格」。
- 最弱面向：每題組取適用面向中等級最低者，並列全列；整場則每面向取各題組（該面向適用者）等級平均，最低者為最弱，並列全列。

## 圖片（考官備註附圖）

- **怎麼存**：檔案放在私有 bucket `assess-notes`（不公開、單檔 2MB、只收 jpeg／png／webp），路徑慣例 `{考核id}/{題組id}/{uuid}.jpg`；資料庫的 `assessment_item_images` 記路徑、格式、大小。前端用「簽名網址」顯示圖片。
- **流程**：前端先傳檔到 Storage → 呼叫 `assess_add_image` 登記；要刪就呼叫 `assess_remove_image`，拿到路徑後再去 Storage 刪檔。
- **限制**：每題組最多 5 張、每張 2MB 內、三種格式；只有草稿能增減，送出或作廢後圖片保留、不可再增刪。
- **Storage 讀取規則**：客服部全看；主管、店長只讀得到路徑第一段（考核 id）對應的考核「已送出」且在其權限內（店長僅限自己門市）的檔案。路徑第一段不是合法 uuid 時視為無權限，不會報錯。沒有「覆蓋」權限：要換圖請刪掉再傳新的。
- **Storage 寫入規則**（客服部也不能繞過函式直接打 Storage API 亂寫）：
  - 上傳：路徑必須是 `{考核id}/{題組id}/{uuid}.jpg|png|webp`，第一段對應的考核必須存在、是草稿、考官是本人，第二段題組必須屬於該考核。已送出、作廢的考核路徑下不能上傳。
  - 刪除：第一段對應的考核是「本人的草稿」，或「已不存在」（`assess_abandon` 刪掉考核列之後，前端要能清掉孤兒檔）。已送出與作廢考核的圖片不可刪。
  - 張數上限：Storage 的上傳規則**沒有**張數上限；每題組最多 5 張由 `assess_add_image` 函式控制（所以請一律走「先傳檔、再登記」流程，登記被拒就要把剛傳的檔刪掉）。單檔 2MB 與格式則由 bucket 設定限制。
- **隱私提醒**：圖片可能含客人個資（對話截圖、車牌、電話）。**客服部、總公司主管、該門市店長都看得到**（僅限已送出的成績單；草稿與作廢的只有客服部）。請提醒考官上傳前遮蔽不必要的個資。
- **已知限制**：
  - **「考核不存在」的路徑任何客服部都能刪**（為了清孤兒檔）。可接受的理由：只有客服部能刪；考核不存在代表這些檔案已沒有任何成績單引用，不會影響任何現存成績單；路徑要符合 uuid 格式才算，不能用亂寫的路徑刪別人的檔；客服部本來就是可信任的內部角色。
  - 放棄考核時，資料庫會回傳圖片路徑清單，**需前端依清單刪除 Storage 檔案**；若前端中途失敗，可能留下沒人引用的「孤兒檔案」（只佔空間，無法經由系統看到，客服部可到 Supabase Storage 手動清理）。
  - Supabase 免費方案的儲存空間約 1GB，圖片多了要留意用量。
  - 作廢的成績單圖片仍保留在 Storage，只有客服部看得到。

## 五、怎麼執行（老闆同意之後）

1. 前提：`roster_schema.sql` 與考題抽選器的 `schema.sql` 都已執行過。
2. Supabase 專案 → SQL Editor → New query → 貼上 `assess_schema.sql` 整份 → Run。可重複執行，不會刪資料。
3. 再開新的 query → 貼上 `assess_verify_fake.sql` 整份 → Run。它只用假資料，**結尾一定 rollback，不留任何資料**。

## 六、驗證結果表怎麼看

執行完 `assess_verify_fake.sql` 後，最後一個結果是一張表，欄位為「序號／測項／預期／實際／通過」：

- 第 0 列「總結」會寫 `N/M 項通過`。**「通過」欄全部是「通過」才算驗證成功**。
- 有「失敗」的列：看「預期」與「實際」差在哪；測項名稱前半是分組（純計算、權限矩陣、流程、舊抽選器）。
- 某個區段若出現「意外中斷」，代表該區段有沒預期到的錯誤，「實際」欄就是錯誤訊息，請整張表貼給我。
- 因為 SQL Editor 只顯示最後一個結果，腳本把結果存在連線層級的預備陳述式（只含結果文字，不含資料）再 rollback、最後才顯示。為保險，rollback 前還會先顯示一次同樣的表，所以可能看到兩張一樣的表，看最後一張即可。
- 驗證會用掉幾個題庫流水號（rollback 也不會倒退），無害。

## 七、已知行為與已知限制

### 已知行為
- **調店後，舊成績單仍屬原門市**：成績單的門市歸屬用開始考核當下的門市快照（`store_code`），員工之後調店不會改。店長看得到的範圍以這個快照為準；調店員工的可見規則老闆之後再決定。
- **姓名也是快照**：成績單列表的姓名取自 `employee_label`（開始考核當下的暱稱或姓名），員工之後改暱稱、調店都不影響列表顯示，列表不依賴名冊。
- **同一位考官對同一員工重複開始考核**（含兩個請求同時進來）：不會報錯，回傳既有那張草稿。

### 抽題排序的取捨
挑題優先順序是：①該考生沒考過 ＞ ②本輪還沒被抽過 ＞ ③不是該分類上一次抽出的 ＞ ④隨機。
因為「該考生考過」優先於「本輪已被抽過」，重考者可能抽到本輪已被別人抽過的題。這符合老闆「優先避開考生考過的題組」的要求，是已知取捨。

### 已知限制
- 放棄考核時**不還原 `category_last`**（各分類最近一次抽出的題）。
- 若放棄期間該分類已開新一輪，放棄可能誤刪別場剛抽的 `drawn` 記錄（極少見）。
- 驗證腳本的結果表輸出若失敗，仍會 rollback，不會留下資料。

## 八、Storage 手動檢查步驟（驗證腳本無法完全取代）

驗證腳本 3-7 會檢查 bucket 設定、policy 內容，以各角色讀取 `storage.objects` 的可見範圍，並測試 insert policy（路徑格式、非草稿、非本人、第二段題組不屬於該考核等，假物件列在交易內，rollback 後消失）。**腳本不測 delete**：Supabase 的 `storage.protect_delete` 觸發器會擋直接 delete `storage.objects`，所以刪除規則一律用下面的手動步驟驗證。
該段依賴 Supabase Storage 的表結構，若出現「區段 3-7 意外中斷」，請改用以下手動檢查（需要真實登入帳號）：

1. Supabase 後台 → Storage：確認有 bucket `assess-notes`，狀態為 Private，檔案上限 2MB，允許格式為 jpeg／png／webp。
2. 以客服部帳號登入前端，在草稿題組上傳一張圖並登記 → 預期成功；再傳 6 張 → 第 6 張被拒；傳 gif 或超過 2MB → 被拒（Storage 與函式雙重擋）。
3. 送出該成績單 → 以總公司主管帳號登入：看得到圖片；以該門市店長登入：看得到；以其他門市店長登入：看不到。
4. 另開一張草稿並上傳圖片 → 主管與店長都看不到；作廢一張已送出的成績單 → 主管與店長都看不到它的圖片。
5. 以主管、店長帳號嘗試上傳或刪除 `assess-notes` 的檔案 → 預期被拒。
5-1. 上傳規則（用 Storage API 或儀表板，以客服部帳號）：已送出或作廢考核的路徑下上傳 → 預期被拒；別人建立的草稿路徑下上傳 → 被拒；檔名不是 uuid、副檔名是 gif、路徑少一層 → 被拒。
5-2. 刪除規則（必須用 Storage API／儀表板的「刪除」，不要直接 delete `storage.objects`）：刪自己草稿的圖 → 成功；刪已送出或作廢考核的圖 → 預期被拒；刪別人草稿的圖 → 預期被拒；放棄草稿後（考核列已不存在），依回傳清單刪孤兒檔 → 成功；用隨便捏造的路徑（第一段不是 uuid）刪 → 被拒。
6. 放棄一張有圖片的草稿 → 確認前端依回傳清單把 Storage 檔案刪掉（Storage 裡不再有該路徑）。

### 哪些只能用讀的確認（誠實標示）
- 以上所有 SQL 從未實際執行過，語法與行為都只能靠閱讀確認。
- `storage.objects` 的 policy 引用 `storage.objects.name`、`split_part`、巢狀 RLS（policy 內查 `assessments` 會套用其 RLS）的行為，是依 PostgreSQL 與 Supabase 的一般行為判斷，沒有實測。
- 驗證腳本 3-7 直接 insert `storage.objects` 假列（不做 delete），Supabase 後續版本若有額外觸發器或限制，可能需要調整。
- **delete policy 完全沒有自動測試**，只能靠上面 5-2 的手動步驟與閱讀 policy 確認；`storage.protect_delete` 觸發器的實際行為也是依一般說法判斷，沒實測。
