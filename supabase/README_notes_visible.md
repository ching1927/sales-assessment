# 考官備註文字開放給主管與店長看（notes_visible）

> ⚠️ 目前只是「寫好檔案」，**尚未在 Supabase 執行**。要等老闆同意後才執行。

## 這次變更的目的與範圍

老闆的決定：**考官備註的「文字」，總公司主管與店長也要看得到**，範圍和備註附圖一樣：

| 誰 | 看得到哪些備註 |
|---|---|
| 客服部 | 全部（含草稿、已作廢） |
| 總公司主管 | 全部「已送出」且未作廢的成績單 |
| 店長 | 只有「自己門市」且「已送出」未作廢的成績單 |
| 草稿、已作廢 | 只有客服部 |

**題組名稱、步驟、考點仍然只有客服部看得到**，這次完全沒有放寬（機密表 `assessment_item_secrets` 的權限一個字都沒動）。

做法：原本備註文字放在機密表，主管與店長讀不到；現在改放在 `assessment_items` 新欄位 `note`。
誰看得到，由成績單本來就有的權限規則決定（資料庫的「列層級權限」會自動套用到新欄位），所以不用另外寫新規則。

## 這支 SQL 做了什麼（`notes_visible_schema.sql`）

整份是**一個交易**（開頭 `begin;`、結尾 `commit;`），中途任何一步報錯就整份回復，什麼都不會改。

1. **新增欄位** `assessment_items.note`（可為空）。
2. **搬舊備註**：把機密表舊的備註複製到新欄位。只搬「新欄位是空的」那些列，**不會覆蓋**已有的內容。
3. **清空舊欄位**：搬移後，凡是「新欄位已有值」的列，把機密表對應的舊備註設為空（欄位本身保留不刪）。
   這樣之後使用者把備註清空時，重跑這支 SQL 不會把舊備註從舊欄位「復活」。
4. **改寫 `assess_save_item`（暫存評分的函式）**：備註改寫進新欄位。
   除此之外所有檢查（只限草稿、只限本人、七面向與四級或「不適用」、不適用最多 2 個、可只填一部分、備註不限字數）一字不改。
   檔頭有逐行的「與原函式差異」說明。
5. 重做這個函式的執行權限（與原本相同）。

## 舊欄位已停用

機密表的 `assessment_item_secrets.note` **保留不刪**，但**已停用：不再寫入、也不再讀取**。
**搬移後，已搬到新欄位的列，舊欄位已清空，舊欄位不再使用。**
（「新欄位本來就是空、舊欄位只有空白字元」的列不動，視為沒有備註。）
之後確定都沒問題，再由老闆決定要不要把整個舊欄位拿掉。

## 執行時機與空窗期（請務必看）

- **請選在沒有人暫存備註的離峰時段執行。**
- 為什麼用單一交易：搬移資料和替換函式如果分開執行，中間有人用「舊函式」暫存備註，備註會只寫進舊欄位、沒被搬到新欄位。
  整份放在同一個交易裡，搬移與函式替換是「同時生效」，就不會有這段空窗。
- 即使如此，「按下 Run」到「交易提交」之間（通常幾秒內），若有人正在用舊函式暫存，那筆備註仍可能只寫進舊欄位。
  所以才要選離峰。執行完若懷疑有漏，可再執行一次整份：第 2 段會把「新欄位仍空」的舊備註補搬過來（不會覆蓋任何已有的值）。
  **但這只對「新欄位仍為空」的列有效。**
- **⚠️ 重跑的風險（請特別注意）**：若某列的新欄位與舊欄位**都有值而且不同**，重跑時第 3 段會把舊值清掉，**而且救不回來**。
  首次執行不會發生這種情況（舊欄位本來就沒人再寫）。若需要重跑，**請先備份 `assessment_item_secrets`（或至少記下筆數）**；
  第一次執行前也建議先備份一份，留作保險。
- 關於 Supabase SQL Editor 的 `begin`／`commit`：Editor 會把整份文字當作「一次查詢」送出。
  如果中途有一步報錯，整份交易會自動回復，不會停在半途。所以**不要自己在中途另外按 commit 或 rollback**，貼上整份、按一次 Run 即可。
  （本專案的驗證腳本也是同樣的 begin…rollback 寫法。）
  檔案開頭另外設了「等鎖最多 5 秒」：拿不到資料表鎖就報錯並整份回復，不會卡住別人。
- **前端已改好**（見下節）：新前端讀新欄位、舊前端讀舊欄位。所以「執行本檔」和「前端上線」要**緊接著一起做**：
  先執行本檔，馬上上線新前端；兩者之間舊前端會暫時讀不到備註（舊欄位已清空）。

## 怎麼執行（老闆同意後）

1. Supabase 專案 → **SQL Editor** → New query → 貼上 `notes_visible_schema.sql` 整份 → **Run**（只按一次）。
   前提：`assess_schema.sql` 已經執行過。
2. 馬上上線新前端。
3. 再開一個新的 query → 貼上 `notes_visible_verify_fake.sql` 整份 → **Run**。
   這個驗證腳本只用假資料，最後一定 rollback，不留任何資料。
   **請同樣選離峰時段執行**：區段 2 會對整個資料庫跑一次搬移與清空舊欄位（都在交易內、最後 rollback，不會真的改到資料），
   但交易期間會暫時鎖住真實的備註列，若此時有人暫存備註會被短暫卡住。
   前提：`assess_schema.sql`、`backoffice_schema.sql` 與本檔都已執行（可見性檢查會實際查後台的兩個檢視）。

## 如何還原

- **恢復舊版函式**：`notes_visible_schema.sql` 最下方有「還原腳本」（已寫成註解）。把註解符號拿掉後在 SQL Editor 執行，就會把 `assess_save_item` 換回舊版（備註寫回機密表）。
- **因為第 3 段已清空舊欄位，還原時必須一併執行還原腳本的 (b)「回填舊欄位」**，把備註從新欄位補回舊欄位，否則舊版函式的使用者會看到備註消失。
- 新欄位 `assessment_items.note` 留著無害；真的要移除，執行 `alter table public.assessment_items drop column note;`（會連同裡面的備註一起刪掉，執行前請確認已回填）。

## ⚠️ 風險提醒（請轉告所有考官）

**備註文字現在主管與該門市店長都看得到。**
考官**不要把題組腳本或考點原文貼進備註**（備註附圖同理：不要截圖題組內容）。
備註請寫「這次考核的觀察」，例如「第 2 步回答不夠具體」，不要寫題目本身的內容。
題組名稱、步驟、考點本身仍然只有客服部看得到，這個前提要靠考官自己守住，系統沒辦法判斷備註裡寫了什麼。

## 已知限制

- 備註不限字數（維持現狀），超長備註會一併顯示給主管與店長，前端排版要能處理。
- 已作廢的成績單，備註（與題組、圖片）對主管與店長一併看不到，只有客服部看得到。
- 已送出或作廢的成績單，備註不可再改（與原本一樣，只有草稿能暫存）。
- 搬移時，新欄位已有值的列以新欄位為準，舊值不會覆蓋，且舊欄位會被清空（舊值就不再保留）。
- 舊備註只有**半形空白**的，視為沒有備註，不搬移也不清。含 tab、換行或全形空白的備註，資料庫（`btrim` 預設只去半形空白）不視為空白，會照一般備註搬移與保留；暫存備註的函式與原函式一樣，也只認半形空白。
- 「按下 Run」到「交易提交」之間若有人用舊函式暫存，備註可能只寫進舊欄位（見「執行時機與空窗期」，重跑一次可補搬）。
- `demo_seed.local.sql` 尚未改成寫新欄位（只影響本機示範資料）。
